# دليل تشغيل تسليم العميل — Nabtiq (Client Delivery Runbook)

> المبدأ: النظام لا يعمل وحده. أنت تقود جلسة **Claude Code** على هذا المستودع، وتستدعي
> المهارات (Skills) مرحلةً مرحلة، وتُطلق وكلاء المراجعة (subagents)، وتُصدر أحداث الموافقة
> الموثّقة عند البوّابات. الضمان الوحيد الذي يقدّمه النظام: **لا يُنشَر شيء لم يجتز البوّابات
> الحتمية الـ15 + الموافقات البشرية المطلوبة**. سجلّ الأحداث (`events/`) هو ذاكرة المشروع
> وسجلّ التدقيق في آنٍ واحد.

---

## المرحلة 0 — تجهيز الجلسة (مرة واحدة لكل عميل)

1. اسحب أحدث نسخة من المستودع (هو نظام التشغيل نفسه):
   ```bash
   git clone https://github.com/ibra2000sd/nabtiq-delivery-system
   cd nabtiq-delivery-system      # أو: git pull إن كان موجوداً
   ```
   المستودع يحمل: `.claude/skills/` (13 مهارة قدرة)، `.claude/agents/` (7 مراجعين)،
   `probes/` (16 فاحصاً)، `scripts/`، و`.github/workflows/` (البوّابات + النشر + المراقبة).
2. افتحه في Claude Code، وأنشئ مجلّد المشروع للعميل:
   ```bash
   mkdir -p projects/<client-slug>
   ```
   هذا المجلّد هو **ذاكرة المشروع كاملةً**: حالته، أدلّته، وسجلّ أحداثه. أنشئ فيه
   `profile.json` (الملف الشخصي: النوع، اللغة الأساسية/الثانوية، السوق) — كما في `projects/demo-fixed`.

## المرحلة 1 — الاستقبال + سجلّ الحقيقة (داتا العميل تدخل هنا)

- **المهارات:** `client-onboarding` ← `intake-and-truth-ledger` ← `product-content-research`
  (بحث مصدرٍ أوّليّ فقط للدعاوى التي تحتاج سنداً خارجياً).
- **المخرجات:** `projects/<client>/truth-ledger.json` — كل دعوى واقعية تُستخرَج بنموذج الحقيقة
  رباعي الأبعاد (evidence_status / claim_risk / publication_mode / required_approver_role).
  الحقول الأساسية (اسم، سنة تأسيس، ترخيص، تواصل…) **لا تكون "unknown" أبداً**: إن لم يزوّدها
  العميل، تُعلَّم "بانتظار تأكيد العميل" — لا تُختلَق.
- **البوّابة:** `truth_ledger_lint` (تحجب الدعاوى بلا سند والحقول الأساسية المفقودة).
- **المراجع البشري:** وكيل `truth-claim-reviewer` + موافقة بشرية موثّقة (issuer≠author) للدعاوى
  عالية الخطورة. **تذكّر الحدّ الصادق:** الدعوى المعقولة لكن الخاطئة (مثل سنة تأسيس مغلوطة)
  لا يمسكها الفاحص — يمسكها هذا المراجع + تأكيد العميل. لا تتجاوز هذه الخطوة.

## المرحلة 2 — بنية المحتوى + التأليف ثنائي اللغة

- **المهارات:** `content-architecture` + `seo-structured-content` (بنية الصفحات وكل
  `pages/*.content.json`)، ثم التأليف بالتسلسل: `arabic-authoring` ← `english-adaptation`
  (أو العكس حسب اللغة الأساسية في `profile.json`) — **تطابق الحقائق لا الكلمات**.
- **البوّابات:** `content_lint`، `bilingual_parity_check` (تطابق الأرقام/التواريخ/الأسماء
  بين اللغتين).
- **المراجعون:** `content-ia-reviewer`، `english-quality-reviewer`، و`arabic-native-reviewer`
  (الفصاحة العربية — صنفٌ بشريّ بحت لا يقيسه أي فاحص).

## المرحلة 3 — الهوية + نظام التصميم + الصور

- **المهارات:** `brand-strategy`، `design-system` (رموز التصميم/tokens)،
  `art-direction-image-plan`، `image-generation`.
- **المخرجات:** `image-manifest.json`، `design-tokens.json`، والأصول في `assets/`.
- **البوّابات:** `image_plan_check` (يمنع بديل SVG، يفرض متغيّر الوضع الداكن، يتأكّد من وجود
  الأصول)، `contrast_audit` (WCAG AA للألوان الصلبة؛ النص فوق صورة يُعلَّم HYBRID لمراجعة بشرية).
- **الفاحص الوقتي:** `first_paint_probe.mjs` (Playwright) على النسخة المبنيّة — يمسك وميض
  الـSVG-قبل-الصورة (عطل Golden-Tur الفعليّ).
- **المراجع:** `visual-qa-reviewer` (حكم "الإبهار" قرارٌ بشريّ).

## المرحلة 4 — التنفيذ + الأداء + الأمن/الخصوصية

- **المهارات:** `tech-architecture`، `web-implementation` (HTML دلاليّ، RTL عبر الخصائص
  المنطقية، بطل نقطيّ مع `fetchpriority`، تحليلات خلف موافقة)، `page-experience-composition`.
- **البناء:** `scripts/build_site.py` (أو المكدّس الحقيقي للمشروع).
- **البوّابات:** `perf_budget_check`، `secrets_scan`، `header_csp_scan`،
  `privacy_scan` (PDPL — الموافقة-أولاً سياسة Nabtiq)، `sca_triage` (يحجب KEV/المؤكَّد/الأسرار
  فقط، لا كل "High").
- **المراجعون:** `accessibility-reviewer`، `performance-reviewer`.

## المرحلة 5 — النشر ← التحقق المباشر ← المراقبة

- **جاهزية النشر:** أنشئ `release-candidate.json` (rollback_target + gates_green:true)، ثم
  **أصدر حدث `deployment-authorization` الموثّق** (issuer≠author، role: owner/release-manager)
  في `events/`. البوّابة `deploy_readiness` ترفض النشر بلا تراجع ذرّي وبلا هذا الحدث.
- **النشر الفعليّ:** عبر workflow `nabtiq-deploy` (تشغيل يدويّ + بيئة `production`). **الخطوة
  البديلة (placeholder) في `deploy.yml` تنتظر مضيفاً حقيقياً** — ويمكن ربطها الآن بـ **Hostinger**
  (متاح كموصّل): نشر موقع ثابت عبر `hosting_deployStaticWebsite` أو
  `agencyHosting_deployNodeStaticWebsite`، وربط النطاق عبر أدوات `DNS_*` و`domains_*`.
- **التحقق المباشر:** `live-verify.json` على **رابط الإنتاج الحقيقي** (لا localhost — البوّابة
  `live_verify` ترفض localhost صراحةً، وهو عطل Golden-Tur). ثم أحداث الموافقة البشرية على
  الفحص البصريّ المباشر والفهرسة.
- **المراقبة:** `monitoring-config.json` **مُسلَّحاً** (uptime/RUM/error-tracking/dep-vuln +
  cadence للتحديث) → البوّابة `monitoring_state_check`. وworkflow `nabtiq-monitoring` (cron
  يوميّ) يعيد تشغيل `sca_triage` + يتأكّد أن المراقبة تبقى مُسلَّحة.

## الحلقة الدائمة (تعمل طوال المراحل)

- **hook محلّي** (`PostToolUse`): كل تعديل يشغّل الفاحص المناسب فوراً كتغذية راجعة سريعة.
- **بوّابة CI** (`nabtiq-gates`): كل push/PR يشغّل سلسلة الـ15 فاحصاً + شهادة موقّعة
  (Sigstore/Rekor). لا دمج ولا نشر ما لم تكن خضراء — فعّل **branch protection** على `main`
  لجعل هذا حجباً حقيقياً.
- **سجلّ الأحداث** `events/*.jsonl`: ذاكرة المشروع + سلسلة الإسناد غير القابلة للإنكار.

الأعمى كان الدليل: موقع معطوب كان سيُنشَر لولا هذه الطبقة البشرية.
